DataGEMS · Dataset Profiler · Proposal

Profiling {JSON} files as searchable record sets

Today the profiler lists JSON files in a dataset but never opens them. This proposal defines what a JSON profile should contain so a Kaggle-style catalogue can search inside JSON data, and lists what the Profiler, MoMa and DMM teams each need to do to carry it end to end.

Status Draft for discussion Date 13 Oct 2026 Owner Dataset Profiler Needs input from MoMa, DMM, CDD
Core idea

A JSON file becomes a record set. Its fields are JSONPaths instead of column names, so it is profiled like a table.

Plus text

Long string values (descriptions, notes, abstracts) are chunked like .txt files, so semantic search reaches inside them.

Reuse

The CDD shape mirrors CSV columns and document chunked_content. Existing indexers keep working and the JSON-only keys are additions.

01 · Gap analysis

Where we are today

A .json file already appears in the dataset inventory with the right MIME type, and MoMa even has JSON / JSONSet labels for it. Nothing reads the content, so a JSON-only dataset reaches search as a list of file names.

ComponentBehaviour for a JSON file todayState
Profiler · distribution Listed as cr:FileObject with encodingFormat: application/json (.jsonl → application/jsonl). dataset_profiler/profile_components/distribution.py, SUPPORTED_EXTENSION_MAP works
Profiler · record sets No record set. extract_record_sets_of_file_objects handles only .csv and .xlsx; get_file_type for folders handles only .txt and .pdf. record_set/record_set_extractor.py missing
Profiler · CDD profile Stub entry only: {file_object_id, original_format: "json", source_file, name, description: "", keywords: []}. No fields, no content. profile_models.py, to_dict_cdd() unmatched-distribution branch stub
MoMa · mapping Labels JSON / JSONSet for application/json. application/jsonl is a TODO. The Field spec has variants only for CSV, SQL and XLSX sources, so a field sourced from a JSON file would be stored with no labels and no properties. moma_management/domain/mapping.yml partial
DMM · search & query DatasetType has no JSON / JSONSet, so /dataset/search?types= cannot filter on them. The polyglot query builds views only for text/sql and text/csv; any other MIME type is logged as unsupported. dmm_api/resources/dataset.py, DatasetType, execute_query_mixed() partial
02 · Input

What JSON looks like in real datasets

Unlike CSV, JSON has no single record layout. The first job of the profiler is to work out where the records are. That location becomes the record_path, and every field path is written relative to it. Four shapes cover nearly every open-data JSON file we have seen.

array_of_records 
[
  {"id": 1, "city": "Athens"},
  {"id": 2, "city": "Patras"}
]

Root is an array of objects. record_path = $[*]. Closest to a CSV.

json_lines 
{"id": 1, "city": "Athens"}
{"id": 2, "city": "Patras"}

.jsonl / .ndjson, one object per line. Streams trivially. Lines that fail to parse are counted, not fatal.

wrapped_records 
{"meta": {"source": "NOA"},
 "data": {"items": [
   {"id": 1}, {"id": 2}
 ]}}

API dumps. The largest array of objects wins: record_path = $.data.items[*]. Scalars outside it go to document_metadata.

file_per_record 
articles/
  a-0001.json
  a-0002.json
  …

A folder (MoMa JSONSet) where each file is one record. Profiled as one record set over all files.

A file with no array of objects at all (a config, a single report) is a single_document. It is profiled as one record: structure, metadata and summary, without distribution statistics. Known dialects (GeoJSON, JSON-LD, JSON Schema, OpenAPI) are detected and recorded in dialect. Jupyter notebooks stay listed but unprofiled.

Absent counts as missing

A record without the key and a record with the key set to null both count as missing, the same as an empty CSV cell. notes is missing in 259 of 412 stations, so its missingPercentage is 63%, and queries across CSV and JSON fields mean the same thing.

Arrays become repeated fields

Paths under [*] are marked repeated and get array-length statistics. Their value statistics are computed over all elements: 98 880 readings, not 412 stations.

Mixed types are flagged

elevation_m is an integer in 400 stations and a string such as "n/a" in 12. CSV would silently read the whole column as text. JSON keeps the types, so the profile can report the conflict.

04 · Characteristics

06 · Limits

Guardrails for messy JSON

SituationRule
Objects used as maps{"2019": {…}, "2020": {…}}, keys are IDs or datesIf an object shows more than 50 distinct keys across records and the keys look like data, collapse it to one wildcard path $.x.* with key_samples. Without this, path counts explode.
Very wide or deep schemasAt most 300 paths and depth 8. Anything deeper becomes a single object field and paths_truncated: true is set.
Large filesStream with ijson, never json.load, so memory stays bounded like the CSV chunking. Counts, missing values and min/max are exact. Medians, percentiles and top values come from a 10 000-record reservoir, and sampled: true is set.
Invalid JSONWhole-file JSON: listed, with parse_errors: 1 and no fields. JSON Lines: bad lines are skipped and counted.
EncodingReuse resolve_encoding(). RFC 8259 requires UTF-8, but real exports are not always compliant.
LLM failuresAs for CSV: summary and semantic types are enrichments. A failure is logged and the profile still ships.

MoMa · next steps

moma-management · domain/mapping.yml, domain/schema

MoMa already has JSON / JSONSet distribution labels. What is missing is everything below the file: the record set and its fields. Following the README's "Updating the MoMa model" procedure, this is schema, then make gen, then mapping.

  1. M1

    Map application/jsonl

    mustmapping.yml

    Resolve the existing TODO. JSON Lines should get the same labels as JSON. The encodingFormat property still tells them apart.

    - case: "encodingFormat == 'application/jsonl' && @type == 'cr:FileSet'"
  value: [ "JSONSet", "Data", "@type" ]
- case: "encodingFormat == 'application/jsonl' && @type == 'cr:FileObject'"
  value: [ "JSON", "Data", "@type" ]
  2. M2

    Add a Field variant for JSON sources

    must · blocks P4mapping.yml

    Without this, resolve_variant falls back to the base Field spec, which has no labels or map, so JSON fields would be stored as empty, unlabeled nodes. Keeping the Column label means existing Column queries and the statistics edge keep working, and JSONField adds the JSON-specific properties.

    - when: "_source.encodingFormat == 'application/json' || _source.encodingFormat == 'application/jsonl'"
  type: JSONField
  labels: [ "Column", "JSONField", "@type" ]
  map:
    type: "@type"
    name: name
    description: description
    dataType: dataType
    semanticType: semanticType
    sample: sample
    jsonPath: source.extract.jsonPath
    repeated: repeated
  edges:
    - { from: parent, to: self, label: field }
    - { from: self, to: source.fileObject.@id, label: source/fileObject }
  3. M3

    New node schema jsonField.schema.json

    mustdomain/schema

    allOf the Column schema plus jsonPath (string) and repeated (boolean). Register it in node.schema.json and run make gen. Check edge_constraints.json so that field, source/fileObject (→ JSON) and statistics accept a JSONField.

  4. M4

    Add a RecordSet variant for JSON sources

    shouldmapping.yml

    Same pattern as the existing PDF and text/plain variants: map recordPath, jsonShape, recordCount, maxDepth, schemaConsistencyPercentage, summary and keywords. recordPath is what DMM needs to query the file (D3), so in practice this blocks D3.

  5. M5

    jsonTypes and topValues on Statistics

    mustcolumnStatistics.schema.json

    Two optional string properties, JSON-encoded like histogram. Statistics is in the mapping engine's schema registry, so any property the schema does not declare is dropped silently. CSV columns can use topValues too once the profiler emits it for them.

  6. M6

    Fixtures and ingest tests

    mustassets/profiles

    Start from moma_json_stations_heavy.json: a complete heavy profile with all 11 fields, ready to drop into assets/profiles/heavy/. Test that the round trip yields JSON → cr:RecordSet → JSONField → Statistics, and that a JSONSet folder links its files with containedIn.

DMM · next steps

/dataset/update forwards the AP to MoMa unchanged, and extract_from_AP already keeps cr:Field and dg:ColumnStatistics nodes. Registration and update therefore need no code change. The work is in search filters and querying.

    mustDatasetType

  2. D2

    musttests/

Today PG2Croissant.map_field copies stored properties as flat keys, so jsonPath comes back at the top of the field instead of under source.extract. CSV column has the same issue.   3. D3

    Query JSON files in the polyglot query

    should · needs M4execute_query_mixed

    Add application/json and application/jsonl branches next to text/csv in query_rewriting, execute_query_mixed and write_views_minimal_extraction. The view is built from the record set's recordPath. Also fetch the record set node in extract_query_from_AP, since it currently reads only encodingFormat, contentUrl and name from the FileObject.

CREATE VIEW json_arg1 AS

CREATE VIEW json_arg2 AS

  4. D4

    Use https://datagems.eu/ns/ for dg:

08 · Rollout

Rollout in three phases

The order is set by dependencies. Phase 1 ships on the profiler alone, because the CDD profile is a file and does not pass through MoMa.

1

JSON is searchable

P1–P3, P5
  • CDD profile carries JSON fields, statistics and chunks
  • Heavy profile is unchanged (flag off)
  • No dependency on other teams
2

JSON is in the catalogue

M1–M6D1, D2, D4P4
  • MoMa deploys first, then the profiler flag is turned on
  • Fields and statistics are visible in MoMa and DMM /dataset/get
  • Search can filter by types=JSON
3

JSON is queryable

D3C1, C2
  • SQL over JSON through DuckDB views
  • CDD facets on shape, dialect and size
09 · Decisions needed

Open questions

  1. CDD key: columns or a new fields?
    Recommended: columns, so CDD's CSV indexing works unchanged. Needs CDD confirmation.
  2. MoMa label: Column + JSONField, or a new ColumnJSON in the style of ColumnCSV?
    Recommended: the dual label, so existing Column-based queries need no change. MoMa to decide.
  3. Separate JSONL label, or reuse JSON?
    Recommended: reuse JSON; encodingFormat already tells them apart.
  4. Path cap of 300 and depth cap of 8: right for partner data?
    To validate on the largest JSON datasets partners plan to upload.
  5. Should topValues also apply to CSV in the same release?
    Cheap on our side. It mainly depends on MoMa M5.
